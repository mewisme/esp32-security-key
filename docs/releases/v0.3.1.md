# MultiKeys v0.3.1

The firmware can now say what it is, and the host tools and the web page can show passkey activity as the key reports it. Same
board support as v0.3.0 (4, 8 and 16 MB ESP32-S3, one firmware file per size) and the same installer.

> **Experimental development firmware — not suitable for protecting important accounts.** It uses a development USB
> VID:PID (`303A:4002`, a placeholder) and a development AAGUID, has no Secure Boot and no flash encryption and is not FIDO
> certified.

## What is new

- **The key reports its build** (MKAUTH `INS 07`, read-only, no button, no PIN): project, version, ESP-IDF version, source commit, the
  SHA-256 of the running image, flash size, chip and revision, flash-encryption and Secure Boot state, why this boot started and for how
  long, and the partition it runs from. The MAC address and serial number are not reported.
  - `multikey device build` prints it; `--manifest firmware-manifest.json` says whether the key runs exactly the app image of that release.
    `device version` and `device info` include it.
  - The web page **Your key** (`/key`) reads it over WebUSB and compares the image with every published release.
  - A key still running v0.3.0 or older firmware answers that it cannot report its build. Flash this release's firmware to get it.
- **Passkey activity** (`multikey device watch`, and the same list on the web page): every passkey registration, sign-in and BOOT-button
  wait the key reports, with the site, the account the site chose, the algorithm, whether the button was pressed, whether the key claimed
  user verification, and the CTAP2 error of a failure. The key sends these without a PIN or a button press (upstream pico-fido behavior):
  any local program that can open the key's WinUSB interface sees them, see `docs/SECURITY.md`. A sign-in with no button press is the
  browser's look-up before it asks for a touch and is shown as such.
- **Firmware fix** (`patches/pico-fido/0004`): upstream built these events in a 64-byte buffer and dropped the whole event when the site
  and account names did not fit; they now use up to 255 bytes and cut long text instead.
- The host tool gains one dependency, `nusb` (pure Rust USB), for `device watch`.

## Which firmware file is for my board?

| Your board | File | Tested |
|---|---|---|
| 16 MB flash | `multikey-firmware-v0.3.1-esp32s3-16mb-fido-dev.zip` | **Hardware verified** for the sources of this release: a local build of them ran on one ESP32-S3 N16R8 (Windows 11, Chrome) |
| 8 MB flash | `multikey-firmware-v0.3.1-esp32s3-8mb-fido-dev.zip` | **Build verified only:** never run on a board |
| 4 MB flash | `multikey-firmware-v0.3.1-esp32s3-4mb-fido-dev.zip` | **Build verified only:** never run on a board |

The published v0.3.1 zips themselves were **not flashed** before the release. What ran on the board was a local build of the same
sources (stamp `0.3.0-dev`), flashed as an update; its build report, its image hash equal to the written file's, and its success
events are in `docs/hw-reports/2026-11-23-build-info-and-passkey-events.md`. Not run on the key: the failure events of the new
firmware and the cutting of long text.

Nothing about the storage layout changed (`git diff v0.3.0 v0.3.1` touches no `sdkconfig`, partition table or board file), so an
update keeps the stored name and keys as before.
