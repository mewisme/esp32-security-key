# MultiKeys v0.3.0

Firmware for ESP32-S3 boards with **4, 8 or 16 MB** of flash (one file per size), a redesigned web installer that picks the right
file for your board and lets you name your key, and the same host tools. The firmware sources and the host tools are unchanged
since v0.2.0 apart from the version number (`git diff v0.2.0 v0.3.0` changes only the `version` lines under `host/` and nothing
under `components/`, `patches/`, the `sdkconfig` files or `partitions.csv`; the board profile file was only renamed to
`boards/esp32s3-boot-button.board`).

> **Experimental development firmware — not suitable for protecting important accounts.** It uses a development USB
> VID:PID (`303A:4002`, a placeholder) and a development AAGUID, has no Secure Boot and no flash encryption and is not FIDO
> certified. Only the 16 MB build has been run on a board, and on one board.

## Which firmware file is for my board?

The number after **N** on the metal module is the flash size in MB (N4, N8, N16; an N16R8 has 16 MB of flash and 8 MB of PSRAM).
The firmware does not use PSRAM. Modules with octal flash (for example N16R8V) and boards without a native USB connector are not
supported.

| Your board | File | Tested |
|---|---|---|
| 16 MB flash | `multikey-firmware-v0.3.0-esp32s3-16mb-fido-dev.zip` | **Hardware verified:** one ESP32-S3 N16R8 (Windows 11, Chrome) |
| 8 MB flash | `multikey-firmware-v0.3.0-esp32s3-8mb-fido-dev.zip` | **Build verified only:** never run on a board |
| 4 MB flash | `multikey-firmware-v0.3.0-esp32s3-4mb-fido-dev.zip` | **Build verified only:** never run on a board |

*Build verified* means: built in CI from this tag, its image headers (flash size, mode, frequency), sizes and the partition table
are checked against the profile, and the credential area is outside what the installer writes. Nothing more. All three
sizes use the same partition table (it ends at 0x300000, under 4 MiB) and the same storage layout.

The published v0.3.0 zips were themselves **not flashed** before the release. The hardware runs used a local build of the same
firmware sources (version stamp `0.2.0-dev`).

## What is new since v0.2.0

- **One firmware per flash size.** The release carries a 4, an 8 and a 16 MB image; every one must build and pass the packaging
  checks or nothing is published.
- **Web installer, six stages** (Get started, Firmware & name, Connect & verify, Review, Install, Finish). It reads the chip, the
  flash size and the flash type (quad or octal, from an eFuse), and picks the matching file by exact flash size. It stops, before
  writing anything, for octal flash, an unreadable flash size, an unsupported chip or a release without that size. Any board other
  than the tested N16R8 type, which includes every 4 and 8 MB board, needs an extra acknowledgement ("this board type hasn't been
  tested") before the Install button works. The interface is available in English and Vietnamese and respects the browser's
  reduced-motion setting.
- **Name your key.** Choose the key's USB name before flashing; after the verified flash the page applies it through the key's
  management channel over WebUSB (you press BOOT, and enter the management PIN if the key has one; the PIN is never stored), then
  reads the name and the USB product string back and says "Applied and verified" only if both match. The same field changes or
  resets the name later on the First use page. If the browser cannot do it, the page shows the equivalent `multikey device
  rename` command. When you install v0.2.0 (or older) from the page, it does not try to rename the key.
- **Manifest schema 2.** The v0.2.0 manifest (schema 1) is still accepted by the installer and treated as the 16 MB build.
- **Developer tools.** `tools/build.py --hw esp32s3-4mb|8mb|16mb --board esp32s3-boot-button` and `tools/flash-dev.ps1 -Hw <profile>`
  (the board's flash size must match the profile exactly before anything is written).
- **Host tools:** rebuilt as 0.3.0, no code change.

## Install the firmware

- **Web installer:** https://multikeys.mewis.me (desktop Chrome or Edge). Run on real hardware on one board (Windows 11, Chrome): updating an existing install,
  naming the key before flashing and renaming it afterwards (`docs/hw-reports/2026-11-23-web-installer.md`,
  `docs/hw-reports/2026-11-23-profiles-and-personalization.md`). A manual replug is still needed after flashing (the browser's
  serial library leaves the chip in download mode). First install, switch and repurpose modes, 4 and 8 MB boards, Linux and macOS
  and renaming a key that has a management PIN have been tested only against simulated hardware or not at all.
- **Manual:** unzip the firmware archive for your flash size and follow its `README.txt` (one `esptool write_flash` command with
  the three offsets). It never erases the whole chip; the credential area (`part0`) is not written.
- **From source:** `tools/flash-dev.ps1 [-Hw <profile>]` as before.

Updating a key that runs the v0.2.0 release: the partition layout and storage are unchanged, nothing in `nvs`, `phy_init` or
`part0` is written, and the web installer offers a normal update. A key built locally (`0.2.0-dev`) or running older firmware does
not declare a data format version; the installer asks you to acknowledge that stored keys are not guaranteed.

## Verify

`sha256sum -c SHA256SUMS --ignore-missing` (Linux) or `Get-FileHash -Algorithm SHA256 <file>` (Windows), compared with
`SHA256SUMS`. Inside a firmware zip: `sha256sum -c SHA256SUMS`. Checksums protect against corrupted downloads, not against a
compromised repository or release; nothing is signed.
