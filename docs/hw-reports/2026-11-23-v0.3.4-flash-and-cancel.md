# v0.3.4 app-only flash and CTAPHID cancel probe on the N16R8

Date: 2026-11-23. Board: ESP32-S3 N16R8 (16 MB), MAC `80:b5:4e:c8:22:78`, Windows 11, `.venv` esptool, host CLI built from `main`.
Image: published `multikey-firmware-v0.3.4-esp32s3-16mb-fido-dev.zip` (tag `v0.3.4`, commit `b92467441aac`, ESP-IDF v5.5.6).
Approved by the maintainer: one app write, the cancel probe and the UV script groups below. No PIN, reset, enrolment, new
credential or eFuse operation was done by these runs. The key already had a FIDO PIN and `alwaysUv=true` (state of the board, not
changed here).

## `tools/ctap_cancel_probe.py` (elevated, no touch): PASS 3/3

| Case | A after cancel | B |
|---|---|---|
| B on a new channel after 2 s | `KEEPALIVE_CANCEL` after 1.30 s | `OPERATION_DENIED` after 15.1 s |
| B on the **same channel immediately** | `KEEPALIVE_CANCEL` after 1.30 s | `OPERATION_DENIED` after 15.1 s |
| B on the same channel after 6 s | `KEEPALIVE_CANCEL` after 1.30 s | `OPERATION_DENIED` after 15.0 s |

The failure of the old firmware (case 2 returning `SUCCESS-REPLY` after about 0 s) did not occur. Observation: A's cancel answer took
1.3 s, more than the 0.14 s of the earlier build and more than the "under 1 s" criterion of `docs/hw-procedures/cancel.md`. The cause
was not investigated.

## `tools/ctap_uv_test.py`

- `--only info raw`: 7 of 8 checks passed. The failing check, "alwaysUv is false", is a precondition for a PIN-less key; this key has
  a PIN and `alwaysUv=true`, so it is not a firmware finding. `uv=true` was refused with `INVALID_OPTION` for makeCredential and
  getAssertion. makeCredUvNotRqd is advertised.
- `--only info raw timeout cancel stale` (first run): the log holds only the device line. The result of `timeout`, `cancel` and
  `stale` is **not known**: it is not known where the run stopped or whether BOOT was pressed at the right time. Not repeated.
- Not run: `nopin` (needs a PIN-less key), `pin` (needs the PIN), browser sign-in with `alwaysUv` on.

## Conclusion

The CTAPHID cancel fix is hardware verified for these three cases on one board. The UV/PIN fixes (`pico-fido/0005`) are not hardware
verified: only GetInfo and the raw option checks ran. The v0.3.4 release was published unflashed; this report is the first run of
its published image.

## Second run: `ctap_uv_test.py --only timeout cancel stale pin` (elevated shell, PIN from `MULTIKEY_TEST_PIN`): 9/9 PASS

The first attempts through `run_elevated.ps1` produced no usable output (its pipe hid the prompt that waits for Enter, and a no-echo
PIN prompt hung before the key was opened); `tools/ctap_hid_probe.py` showed the HID side answering in 0.2 s, so the key was not the
problem. The run below was started directly in an administrator PowerShell. The maintainer entered the PIN and pressed BOOT at the
prompts; the PIN is not in this report or any log.

| Group | Check | Result |
|---|---|---|
| timeout | no touch: request fails after the presence timeout | `OPERATION_DENIED` after 15.1 s |
| cancel | `CTAPHID_CANCEL` aborts the pending request | `KEEPALIVE_CANCEL` 0.14 s after the cancel |
| cancel | GetInfo right after a cancel | answered in 0.26 s |
| stale | request A cancelled | `KEEPALIVE_CANCEL` |
| stale | a press made before request B (new channel) does not satisfy B | `OPERATION_DENIED` after 15.0 s |
| pin | `userVerification=required` with the PIN | UP=1 UV=1, one PIN request |
| pin | discouraged non-resident registration, touch only | UP=1 UV=0, no PIN request |
| pin | discouraged assertion, touch only | UP=1 UV=0 |
| pin | resident-key makeCredential without pinUvAuthParam | `PUAT_REQUIRED` after 0.0 s |

Notes: the cancel answer took 0.14 s here, against 1.30 s in the probe above; the difference between the two tools was not
investigated. All credentials of this run are non-resident (rpId `multikey.test`); nothing was stored, no PIN was set or changed,
no reset. The `nopin` group (needs a PIN-less key) was not run. The new `getAssertion` `alwaysUv` enforcement was not exercised: the
touch-only assertion succeeded, which is consistent with the `alwaysUv` configuration option being off while GetInfo reported
`alwaysUv=true` (inference: GetInfo reports it while the PIN-wrapped key is locked); this was not checked.

## Conclusion (updated)

Hardware verified on one board with the published v0.3.4 image: CTAPHID cancel and same-channel recovery, the user-presence timeout, a
stale press not satisfying a later request, and the PIN-set touch-only / UV behaviour listed above. Not hardware verified: the
`alwaysUv` option turned on (getAssertion refusal, on/off round trip restoring makeCredUvNotRqd), the locked-key refusal path
(`PUAT_REQUIRED` instead of the decoy credential), `nopin`, and browser flows.
