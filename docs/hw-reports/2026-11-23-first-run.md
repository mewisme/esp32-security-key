# 2026-11-23: first run of the fido development image (BOOT button, no LED)

Date: 2026-11-23
Board: ESP32-S3 (QFN56, rev v0.2), MAC 80:b5:4e:c8:22:78, 16 MB quad flash, 8 MB embedded PSRAM (unused by the firmware).
Board vendor/model name: not known. Only the native USB port was connected (no UART bridge port seen).
Host: Windows 11, ESP-IDF v5.5.6, python-fido2 2.2.1, PowerShell, tests run from an elevated shell.
Image: `fido`, dev profile, `sdkconfig.board` = GPIO0 active-low button, LED type NONE. Built from commit `01f821d`
(`fix: enforce FIDO user presence ...`) with patches/ applied. VID:PID 303A:4002 (development placeholder).
Fuse state before and after: all Secure Boot / flash-encryption / JTAG / download-restriction bits 0
(`tools/provision_check.py`, before flashing). No eFuse was written by anything in this session. No authenticator reset,
no erase of key storage (the key-storage partition at 0x200000 was blank before the first flash). The vendor image that was
on the board was overwritten (user declined a backup).

## Build and configuration checks
- Real-pin build (no `--ci-pins`) of the fido image succeeds: 0x97a40 bytes, 68% of the 1.88 MB app partition free.
- Generated config: Secure Boot off, flash encryption off, `MULTIKEY_ALLOW_EFUSE_PROVISIONING` off, `UNSET_PINS_FOR_CI` off.
- `tools/check_no_irreversible.py fido-dev`: PASS.

## Flashing and enumeration
- esptool through the native USB-Serial/JTAG port (COM6) works; flash 16 MB confirmed; write and hash verification OK (3 flashes).
- After flashing the device enumerates as `303A:4002`: two HID interfaces, `Microsoft Usbccid Smartcard Reader`, WinUsb
  interface. COM6 disappears (TinyUSB owns the PHY), as expected.
- **Finding:** with `--after hard_reset`, a chip that was flashed from download mode stayed in download mode
  (`rst:0x15 USB_UART_CHIP_RESET, boot:0x23 DOWNLOAD(USB/UART0)`) until a normal power-cycle. `--after watchdog_reset` boots the
  firmware directly. FIRST_RUN_WINDOWS.md updated.
- No boot log captured: the console is UART0 and this board's native port carries only USB.

**Unexplained observation:** on the re-flashed image, the first no-touch run reported `success after 10.6s` with an UP-needed
keepalive, i.e. a button press was registered at about 10 s. The person at the board may have pressed BOOT early (the
instructions for the next phase were on screen); a spurious input cannot be excluded. Five further no-touch runs on the same
image (4 in one batch + 1 via `run_elevated.ps1`, about 75 s of idle time) all ended with `OPERATION_DENIED` after 15.1 s.
Treat as open until a longer idle test is done.

An earlier smoke run showed one ES256 failure (`OPERATION_DENIED`) when the first touch prompt appeared before the tester was
ready; the re-run passed. Not a firmware fault as far as can be told.

## CCID / MKAUTH (read-only)
`multikey readers` lists `MultiKey (dev) ESP32-S3 MultiKey CCID OTP FIDO 0` (before the string fix: `Pol Henarejos Pico Key CCID ...`).
`multikey status`: protocol version 1, enrolled false, policy 0x01, device id all zero. SELECT + GET_INFO work through
Windows PC/SC and the CCID interface. ENROLL / CHALLENGE / REVOKE were **not** run (they change key-storage state).

## Credentials left on the device
Two resident test credentials for rpId `multikey.test` (one EdDSA, one ES256). They cannot be removed without setting a PIN
(credential management) or a reset; harmless, left in place deliberately.

## Not verified
